# Your knowledge work agent has no referee

When you build a coding agent, you get verification for free. Tests pass or they don't.
The agent knows when it's done.

When you build a knowledge work agent — one that writes strategy, researches markets,
synthesises decisions — you get nothing. Every pass adds polish. Agreement between agents
is not evidence of quality. It might just be homogeneity failure.

This is called the **verification gap**. It was named publicly in September 2026.
It is not yet solved.

---

## The problem with what you've tried

**Single loop**: one agent, one prompt, iterate on output. Expected weakness: no integration
role, no manufactured referee, high-confidence and under-tested.

**Build-critic pair**: builder produces output; critic reviews it. Expected weakness:
self-critique by the same model family is the weakest form of verification. The critic has
no standing.

**Free mesh (AutoGen-style)**: agents negotiate freely. In production, this largely failed —
loops, deadlock, contradictions, no convergence. See [what survived in 2026](/research/multi-agent-production-2026).

**Flat topology (CrewAI-style)**: roles without structure. Without hierarchy and feedback,
flat topologies amplify error — up to 17.2× versus a single-agent baseline.

---

## The topology approach

The Randow Maps product-manager-bet topology is a multi-agent coordination system
defined entirely in YAML and Markdown. No code required to run it.

Five agents. Each with a role, a knowledge file, and named feedback channels:

<Callout type="info">
**PM** → **Exec** → **Delivery** → **GTM** → **Practitioners** → (return to PM)
</Callout>

Each agent:
- Reads a **SKILL.md** that defines their role and what they must produce
- Maintains a **knowledge file** — a running record of what they know and what they've learned
- Reads the **upstream entity** produced by the previous agent
- Reads **return flows** from agents downstream — correction signal coming back up

The correction signal is the referee. Not a judge you designate. A structure that means
errors surface and travel back to where they can be corrected, rather than compounding silently.

---

## How it works

**An iteration** starts when the PM reads all return flows and updates the aligned bet.
It ends when Practitioners have provided new signal. Every agent in between has acted.

**Bypass loops** are not failure states. They are named tensions:
- Sales → Delivery direct: field requests that don't need PM approval
- Sales → Exec direct: market signals that need viability review before the PM synthesises
- Practitioners → Sales direct: usage feedback that goes to market before it reaches PM

When bypasses are firing, you can see it in the topology. That visibility is the feature.

**The consideration mechanism**: before every action, each agent reads their knowledge file.
That file encodes what *good* looks like for their lens. The Exec agent has viability questions
that function as a gate. The Sales agent has a research discipline that requires verbatim quotes,
not summaries. The PM has a starting question that can kill the bet.

This is the manufactured referee. Not a test suite. An inspectable, improvable approximation of one.

---

## What you need to run it

- An AI agent capable of reading YAML and Markdown files and following structured instructions
- A text editor
- No code. No orchestration framework. No API keys beyond your AI provider.

The topology is the coordination spec. Your AI agent is the executor.

## The moving parts

<CodeBlock language="yaml" filename="base.yaml (simplified)">
{`actors:
  - id: actor0
    label: Product Manager
    action: action0

actions:
  - id: action0
    label: Update the aligned bet
    reads: [entityR1, entityR2, entityR3, entityR4]
    produces: entity0

entities:
  - id: entity0
    label: Aligned Bet
  - id: entityR1
    label: Viability Signal
    type: return_flow`}
</CodeBlock>

Each actor has a SKILL.md. Each SKILL.md tells them:
- What their role is and what they must produce
- What to read before acting (upstream entity + return flows)
- How to know when their output is good enough
- Where to record what they've learned

## How to start

**1. Fork the topology**

The base.yaml, skill files, and knowledge files are open. Fork them. Adapt the actor
roles to your domain. The PM / Exec / Delivery / Sales / Practitioners structure is
one instance of the pattern — not the only one.

**2. Define your actors**

Each actor needs:
- A role statement (what lens they hold)
- A starting question (what they ask every iteration before anything else)
- A knowledge file (what they know, updated after every action)
- A definition of their output (what entity they produce)

**3. Run one iteration**

Start with the PM. Give them the knowledge file and the base.yaml. Ask them to read
the return flows (empty first iteration) and produce an aligned bet. Then hand that
to Exec. Exec certifies or returns it. Continue.

A completed first iteration proves the structure works in your domain. That is enough
to know whether to continue.

# Aligned Bet — Iteration 1

## Starting question (answered before anything else this iteration)

**Why are we still doing this?** Because no located alternative does what we claim: routes real-world
outcome signal back into a knowledge-work loop as the verification mechanism. loopi.tech "closes the
loop" with synthetic AI-persona simulation, not real outcomes — the manufactured-referee approach we
argue fails. Grep.ai owns repetitive, regulated knowledge work where rule-based verification already
exists — a different sub-problem. Six GTM listening cycles found zero prior art doing outcome-return
topology for novel, complex knowledge work. **Nothing uniquely better already exists — but we also
have not yet run the test that would tell us if we are right.** That is iteration 1's job.

## The problem (unchanged, now independently confirmed)

Every great AI capability win shares one property: verification is binary and cheap. Knowledge work —
strategy, discovery, research synthesis, content — has no equivalent. The success-criteria trap: writing
a rubric to evaluate knowledge work requires more domain judgment than doing the work.

**New this iteration:** "Verification gap" is now organic vocabulary in the wild — 8+ independent
posters (11-20 Sep), trend #3 in the Fall 2026 State of AI Report (GTM, entityR3-v0). The problem is
real and named by people who are not us. Practitioner phrasings differ from ours, though: "who decides
which agent is right," "which part of my system actually failed," "no history to check against" —
not "environmental feedback." Our mechanism's language is still ours, not theirs.

## Why existing solutions fail (for our segment) — unchanged, plus one confirmed foil

- **Human-in-the-loop, LLM-as-judge:** as before — substitution or self-defeating cost.
- **Adaptive graph topologies:** optimisation without a fitness function.
- **Grep.ai / probabilistic typing:** confirmed by GTM as occupying repetitive/regulated work with rule-set
  verification. Different sub-problem; monitor only.
- **loopi.tech (confirmed by GTM this iteration):** PMs pay $10-40/month to "validate before you build,"
  using synthetic-persona simulation for verification. This *confirms* buyers pay for validation tooling,
  and gives us a clean foil — real-world outcome vs. simulated outcome — but does not touch our ICP
  (orchestration engineers building agent teams) or use real environmental signal.

## The hypothesis (held lightly, mechanism reframed per Exec's question 1)

**Real-world feedback, re-entering the loop through structured return flows, is the mechanism by which
the verification gap can be partially closed.** The environment is the verifier. The consideration
mechanism (each actor reading the receiver's knowledge file before acting) is *not* verification — it is
input quality, a way of making the work more likely to land, not a way of checking that it did. This
answers Exec's R1 Q1: the knowledge-file read is not "the manufactured referee." That phrasing in
`iteration-0.yaml`'s carried-forward notes is Dan/Loopy's to fix; flagged for them again.

## Evidence threshold for iteration 1 (sharper than iteration 0's, per iteration discipline)

Iteration 0's threshold — "one loop with measurable engagement data feeding back, with observable
improvement in a subsequent iteration" — was never tested. Iteration 1 makes it concrete and
operational, adopting Delivery's D3 rule:

Publish the full ten-post run (5 baseline, 5 verdict-window) with a ledger row per post; at least one
verdict-window draft must contain a change note citing a specific baseline ledger row; read the result
as directional only, given audience size. This is a **process** threshold (did the loop run and produce
a traceable change), not yet a **quality** threshold (did engagement improve) — Exec's Q4 says we may
not have enough n for the latter yet, and we should not overclaim it if we don't.

## Counter-evidence threshold (unchanged in substance, now tied to concrete artefacts)

After the ten-post run: (a) the ledger cannot be filled — GTM cannot read platform numbers reliably at
24h/72h — OR (b) no verdict-window draft contains a ledger-cited change note OR (c) Dan overrides
quality judgment the same way on every post regardless of ledger signal (Exec's "down/revoke" condition).
Any one of these after iteration 1 is grounds to pivot the mechanism, even if the problem framing holds.

## Decision: Continue

Not pivot, not stop. The problem is more confirmed than at iteration 0's close, independently so. No
competitor has been found doing what we propose. But we have zero evidence about the mechanism itself —
positive or negative — because we have not run it. Continuing means running it now, not revising the
bet again on reasoning alone. The ICP supply-side gap (Exec Q2) is real and worth GTM's full attention
next iteration, but it is a reach problem, not yet a signal that the mechanism is wrong.

## Confidence

**Low-Medium on the problem** (up from iteration 0 - now independently confirmed in the wild).
**Low on the mechanism** (unchanged - zero direct evidence, positive or negative; entityR3-v0 found not
one post, for or against, resembling our framing).
